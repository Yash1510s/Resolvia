## 1. Executive Summary

Resolvia is conceived as a hybrid decentralized dispute arbitration platform founded on a core axiom: **"AI assists evidence analysis; an independent human jury makes the binding decision,"** anchored to a **tamper-evident cryptographic ledger**.

A forensic, multi-layered inspection of the codebase reveals that while individual subsystems show significant individual effort, the project currently operates in **divergent architectural silos connected by client-side simulations**:

1. **The Polished Frontend Simulation Layer:**  
   The [frontend](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend) features 21 deep-linkable Next.js 16 routes, a clean dark/violet visual theme, and active client-side state mutation. However, outside of the standalone developer sandbox on [`/protocol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/(app)/protocol) and evidence anchoring via [`EvidenceRegistry`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/EvidenceRegistry.sol), the core user journey—dispute filing, respondent notification, juror appointment, commit-reveal voting, and verdict settlement—runs **in-memory within [AppContext](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/app-context.tsx)**. Transactions are simulated with synthetic hexadecimal hashes generated by `rndTx()`, block numbers are randomized, and state is persisted merely as an opaque 2MB JSON blob dump per user in a SQLite key-value table.
2. **The Smart Contract Suite & Dead-End Integrations:**  
   The EVM layer contains 5 Solidity contracts with 17 passing Hardhat unit tests covering commit-reveal math and escrow settlement. However, [`ArbitrationHub.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/ArbitrationHub.sol) and [`CaseRegistry.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/CaseRegistry.sol) are **completely bypassed** by the 5-step dispute wizard in [`create/page.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/(app)/create/page.tsx). Furthermore, [`CaseRegistry.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/CaseRegistry.sol) exposes `anchorEvidence` and `anchorAIReport` guarded by `onlyHub`, yet [`ArbitrationHub.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/ArbitrationHub.sol) contains no functions to call them, rendering on-chain dispute evidence and AI report roots permanently unreachable.
3. **The AI & ML Advisory Engine:**  
   The AI subsystem has evolved into a dual-engine architecture: a multi-provider LLM pipeline ([`analysis_pipeline.py`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/ai-engine/analysis_pipeline.py)) with OWASP LLM01 prompt sanitization, paired with an offline-trained 119-feature XGBoost classifier ([`ml_predictor.py`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/ai-engine/ml_predictor.py)) reaching 94% test accuracy on synthetic dispute distributions. While recent commits reconciled the Pydantic schema mismatch on [`POST /api/ai/analyze`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/backend/server.py#L100-L146), the frontend still falls back to static hardcoded text whenever the backend is offline, and the UI progress steps in [`AIAnalysisPanel.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/components/AIAnalysisPanel.tsx) are driven by client-side `setInterval` timers rather than real backend pipeline streaming.
4. **Data Isolation & Security Perimeter:**  
   There is **no shared relational database for disputes**. If User A files a claim against User B, User B cannot see it because user state is siloed per account. Additionally, [`backend/secret/keys.json`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/backend/secret/keys.json) contains committed plaintext cryptographic keys (master AES-256 key and JWT secret), and [`POST /api/auth/wallet`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/backend/auth.py#L521-L530) allows unauthenticated session token issuance without cryptographic signature verification (Sign-In with Ethereum / EIP-4361).

Resolvia possesses solid core conceptual primitives and strong standalone components, but it cannot mature into an enterprise or production-grade system until its foundational relational data model, smart contract lifecycles, and security controls are unified into a single verifiable truth.

### Critical Flow Traces

#### Flow 1: Dispute Creation & Evidence Upload
1. Claimant completes the 5-step wizard in [`create/page.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/(app)/create/page.tsx).
2. Evidence files are hashed in-browser via WebCrypto `SHA-256` in [`lib/crypto.ts`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/crypto.ts#L25-L33).
3. The wizard triggers a simulated sequence of `setTimeout` steps displaying "Locking 500 RSLV escrow stake…" and "Registering case on CaseRegistry…".
4. The wizard invokes `anchorEvidenceOnChain` in [`lib/chain.ts`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/chain.ts#L227), which submits evidence records directly to [`EvidenceRegistry.registerEvidence`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/EvidenceRegistry.sol#L39).
5. **Architectural Gap:** [`ArbitrationHub.initiateDispute()`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/ArbitrationHub.sol#L114) is **never invoked**. No stake is locked, and no case is registered on [`CaseRegistry.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/CaseRegistry.sol). The case exists solely inside the claimant's client-side state.

#### Flow 2: AI & ML Advisory Analysis
1. User clicks "Run AI Analysis" on [`cases/[caseId]/page.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/(app)/cases/[caseId]/page.tsx).
2. Frontend sends `POST /api/backend/ai/analyze` with case statement and evidence metadata.
3. Backend [`server.py`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/backend/server.py#L101-L145) receives the request via `AIAnalysisRequest` and forwards it to `EvidenceAnalyzer.analyze_dispute()`.
4. In [`analysis_pipeline.py`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/ai-engine/analysis_pipeline.py):
   - Untrusted inputs are scanned against prompt injection regex patterns.
   - The ML Champion model ([`ml_predictor.py`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/ai-engine/ml_predictor.py)) computes outcome probabilities across 119 features.
   - The cloud LLM (or deterministic fallback) synthesizes timeline events, claim-to-evidence mappings, and contradiction radars.
5. If the backend is offline or errors, [`app-context.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/app-context.tsx#L669-L713) catches the error and silently populates a static mock object.

#### Flow 3: Jury Empanelling & Deliberation
1. When AI analysis completes, [`app-context.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/app-context.tsx#L678) executes `makePanel()`, generating 5 mock juror records with randomized addresses.
2. Deliberation messages in [`jury/[caseId]/page.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/(app)/jury/[caseId]/page.tsx) append to the in-memory case object.
3. **Architectural Gap:** [`ArbitrationHub.appointJurorPanel()`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/ArbitrationHub.sol#L160) is never called. External peers cannot discover the case, receive invitations, or read deliberation posts.

#### Flow 4: Commit-Reveal Voting & Settlement
1. Juror selects a verdict and salt in [`CommitRevealVoting.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/components/CommitRevealVoting.tsx).
2. Component computes commitment using [`lib/commitment.ts`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/commitment.ts) via `keccak256(abi.encodePacked(uint8, bytes32, uint256, address))`.
3. In [`app-context.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/app-context.tsx#L489-L555), `commitVote` and `revealVote` update juror statuses locally, generate fake transaction hashes (`rndTx()`), and tally votes in React state.
4. **Architectural Gap:** The dispute interface bypasses the backend signing endpoints ([`/wallet/vote/commit`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/backend/auth.py#L547)) and [`VotingManager.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/VotingManager.sol). Real smart contract voting occurs strictly within [`OnChainProtocol.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/components/OnChainProtocol.tsx) on `/protocol`.

#### Flow 5: Data Persistence & Multi-Tenant Siloing
1. Client mutations in [`app-context.tsx`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/frontend/app/lib/app-context.tsx#L370-L385) trigger a debounced `PUT /api/backend/state`.
2. Backend [`state_store.py`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/backend/state_store.py#L46-L62) stores the serialized JSON blob into SQLite table `user_state` keyed by user ID (`sub`).
3. **Architectural Gap:** Because data is stored as a single monolithic JSON blob per user, there are no relational tables for disputes, parties, evidence, or votes. Two users on the same platform cannot interact with each other's cases.

## 8. Architecture / Reliability Risks

### Cross-Module Risk Analysis

```
[ Claimant Browser ] ──(1) SHA-256 Hashing ──▶ [ EvidenceRegistry.sol ]
         │                                               │
         ▼ (2) Raw JSON dump                              ▼ (No Linkage)
[ SQLite user_state ]                        [ ArbitrationHub / CaseRegistry ]
         ▲                                               ▲
         │ (3) Isolated Sandbox                          │ (Admin Only)
[ Respondent Browser ] ──────────────────────────▶ [ Backend Operator Key ]
```

1. **Dual Source of Truth / Desynchronization Risk:**  
   The system maintains two completely disconnected state engines:
   - Client-side React state serialized into `state.db`.
   - On-chain state in `CaseRegistry.sol` and `VotingManager.sol`.  
   *Failure Scenario:* If a transaction succeeds on-chain but the browser is closed before the state sync completes, the user's UI reverts to the pre-transaction state while the smart contract has locked their tokens.
2. **Missing Relational Backing for Multi-Party Disputes:**  
   Because user state is stored as a single JSON blob per user, there is no shared record of disputes, evidence, or votes.  
   *Failure Scenario:* User A files a dispute against User B. User B logs in from another machine and sees an empty dashboard. User B cannot counter-stake or submit evidence, causing the dispute to stall indefinitely.
3. **Dead-End Contract Linkage (`CaseRegistry` ↔ `ArbitrationHub`):**  
   [`CaseRegistry.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/CaseRegistry.sol#L93-L100) requires that evidence roots and AI report roots be anchored exclusively by `arbitrationHub`, but [`ArbitrationHub.sol`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/ArbitrationHub.sol) contains no functions to call them.  
   *Failure Scenario:* The backend attempts to anchor an evidence Merkle root on-chain to provide tamper verification. The transaction reverts with `"Only ArbitrationHub"`.
4. **Gas Exhaustion on Mass Juror Reward Distribution:**  
   In [`ArbitrationHub.sol:236-241`](file:///c:/Users/YASH%20VIJAY%20SINGH/Desktop/MLBC%20project%20copy/Resolvia/blockchain/contracts/ArbitrationHub.sol#L236-L241), `distributeEscrow` iterates across the entire `jurorPanels` array and performs ERC-20 token transfers inside an unbounded loop.  
   *Failure Scenario:* If the panel size is expanded or token transfer gas consumption spikes, `settleCase()` runs out of gas, locking all escrowed funds permanently.

## 13. Things We Should NOT Add

To preserve project focus and avoid unnecessary complexity, the following tempting features should be **explicitly rejected**:

1. **Autonomous AI Judges / AI-Finalized Verdicts:**  
   *Why not:* Violates Resolvia's core principle (*"AI assists, humans decide"*). Fully autonomous AI legal decisions create severe regulatory, legal, and hallucination liabilities.
2. **Decentralized Storage DAO / Custom Storage Blockchain:**  
   *Why not:* Over-engineers a problem already solved by IPFS, Arweave, and Filecoin. A dispute arbitration platform needs immutable content addressing, not custom storage consensus.
3. **Complex Multi-Token Governance Economies (veTokens, Liquidity Mining):**  
   *Why not:* Introduces speculative volatility and regulatory exposure without improving dispute resolution fairness. RSLV should remain a simple utility stake and reward token.
4. **Synchronous Real-Time Video/Audio Courtrooms:**  
   *Why not:* High infrastructure cost and latency overhead that distracts from asynchronous, evidence-based commit-reveal arbitration.
5. **On-Chain AI Model Execution (zkML):**  
   *Why not:* Current zkML proving times for LLMs and deep tabular models are prohibitively expensive and impractical for dispute turnaround times. Anchoring model weights and output hashes off-chain is sufficient and auditable.
